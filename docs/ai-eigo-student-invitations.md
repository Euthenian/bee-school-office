# AI-EIGO Student Invitations

Bee School Office is the source of truth for Bee student access to AI-EIGO.

AI-EIGO registration does not independently make someone a Bee student. AI-EIGO must activate the canonical `bee` entitlement only after its server verifies and claims a valid Bee School Office invitation for an existing Bee School student.

## Normal Activation Flow

```text
Bee School Office
-> personal secure invitation email
-> secure personal AI-EIGO link
-> AI-EIGO account creation or login
-> service-side invitation verification and claim
-> verified Bee School student link
-> canonical AI-EIGO bee entitlement activation
-> Bee School Office shows Linked
```

There is no classroom QR code, generic signup QR, shared Bee invitation code, or generic public URL that grants Bee access.

## Invitation State

Bee School Office stores AI-EIGO invitation state in `ai_eigo_student_invitations` and verified account links in `ai_eigo_student_links`.

User-facing states are:

- `Not invited`: no active invitation or the previous invitation expired/failed and needs staff action.
- `Invited`: a Resend invitation was successfully sent.
- `Linked`: AI-EIGO has claimed the invitation and Bee School Office has a verified AI-EIGO user link.

Technical states support safe operations:

- `pending_send`: Office queued the invitation but Resend has not confirmed delivery.
- `sent`: Resend delivery succeeded; the personal token may be claimed until expiry.
- `send_failed`: Resend delivery failed; no token remains claimable.
- `claimed`: the invitation was used and cannot create another link.
- `revoked`: staff resent or the system invalidated the invitation.
- `expired`: the token reached its expiry before claim.
- `manual_review`: AI-EIGO attempted a claim that should not be auto-granted.

## Secure Token Model

Invitation links use a cryptographically random 32-byte token generated by PostgreSQL `gen_random_bytes`.

The raw token is never stored in Office tables. At email dispatch time, the service-role worker asks Bee School Office to prepare the email payload. The database stores only `sha256(token)` in `token_hash`, plus `token_expires_at`.

The invitation expiry rule is 14 days from email preparation. Resending revokes prior active invitations and creates a new queued invitation.

After a successful claim, Bee School Office keeps the token hash until the invitation naturally expires so the AI-EIGO server can safely retry the same claim if its local entitlement activation fails temporarily. The retained hash is used only to identify the same already-claimed invitation; it never makes the invitation generally claimable again.

## Email Flow

Staff click `Send AI-EIGO invitation` or `Resend invitation` in Bee School Office. The browser calls `send_ai_eigo_student_invitation_mvp(student_id)`.

That RPC:

- verifies the authenticated staff member can manage the student;
- requires the student to be active;
- selects the student's primary email from `student_contacts`;
- rejects already-linked students;
- revokes prior active invitations for the same student;
- queues a normal `communications` row and Resend `communication_integration_actions` row.

The existing `communications-dispatch` Edge Function prepares AI-EIGO invitation email payloads just before sending, sends through the server-side Resend provider, and records delivery through `record_communication_integration_result`. Gmail Trial Booking polling remains separate and read-only.

Email failure sets the invitation to `send_failed`, clears the token hash, and leaves a safe retry path.

## AI-EIGO Claim Flow

AI-EIGO must host the invite route, for example:

```text
https://ai-eigo.com/invite/{secure-token}
```

The AI-EIGO browser must not grant itself Bee access. The AI-EIGO server must call Bee School Office service-role-only RPCs:

- `verify_ai_eigo_student_invitation_mvp(token)` to check whether the token is valid, active, unexpired, and unclaimed.
- `claim_ai_eigo_student_invitation_mvp(token, ai_eigo_user_id, ai_eigo_email)` after AI-EIGO login or signup.

On first successful claim, Bee School Office creates one `ai_eigo_student_links` row with `entitlement_code = 'bee'`, marks the invitation `claimed`, stores the claiming AI-EIGO user ID/email, and returns the verified student/link payload to the AI-EIGO server with `claim_status = 'linked'`.

If AI-EIGO retries the same secure link before expiry with the same linked AI-EIGO user ID, Bee School Office returns the same link identity with `claim_status = 'already_linked_same_user'`. It does not create another link, duplicate entitlement data, or move the invitation to manual review.

A claimed invitation remains rejected for any different AI-EIGO user. The verify RPC reports claimed invitations as `invitation_status = 'claimed'` and `claimable = false`; same-user retry semantics belong only to the claim RPC.

AI-EIGO must then activate only its canonical `bee` entitlement for that authenticated user. Bee is not Premium, Pro, AI-EIGO Plus, Avatar access, or an open-ended future Premium grant.

## Existing And New AI-EIGO Accounts

Existing account:

```text
personal invite link
-> AI-EIGO login
-> server claim
-> Bee link and bee entitlement
```

New account:

```text
personal invite link
-> AI-EIGO signup
-> authenticated post-signup claim
-> Bee link and bee entitlement
```

The invitation context must survive AI-EIGO login/signup server-side. Bee School Office does not infer Linked from matching email addresses alone.

## Email Exceptions

Bee School Office sends the invitation to the student's primary email contact. That email may belong to the student or a parent/guardian.

Automatic claiming requires the authenticated AI-EIGO account email to match the invitation recipient email after normalization. If it differs, or if the AI-EIGO account is already linked to another Bee student, Bee School Office moves the invitation to `manual_review` and does not activate Bee automatically.

If the invitation recipient email appears on another Bee student contact row, the claim also moves to `manual_review`. This prevents silent linkage in cases such as shared family email addresses, parent accounts used for multiple children, or students using a different AI-EIGO login email.

## Authorization

Authenticated Office staff can send invitations only through `send_ai_eigo_student_invitation_mvp`, which checks `can_manage_student(student_id)`.

Direct browser inserts, updates, and deletes on AI-EIGO invitation/link tables are not granted. Staff can select rows through RLS only for students they can manage.

The AI-EIGO verify/claim RPCs are service-role only. No service-role key, Resend key, Gmail OAuth secret, or raw token is exposed to the browser.

## Future Revocation

Automatic entitlement revocation for inactive or withdrawn Bee students is not implemented in this phase. The `ai_eigo_student_links` table keeps `organization_id`, `school_id`, `student_id`, `ai_eigo_user_id`, `entitlement_code`, and timestamps so a future enrollment-status synchronization job can revoke or suspend AI-EIGO Bee entitlement cleanly.

## Production Blocker

This repository implements the Bee School Office side of the contract. Production use still requires the AI-EIGO application/server to implement its invite route, call the service-role verify/claim RPCs, and activate the canonical AI-EIGO `bee` entitlement server-side.
